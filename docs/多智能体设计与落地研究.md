# 多智能体设计与落地研究

> 面向 COS/Frappe/FAC/Raven 栈的多智能体（Multi-Agent）设计模式与落地考量。  
> 输出语言：中文。

---

## 1. 概述

### 1.1 多智能体 vs 单智能体

- **单智能体**：一个 LLM 实例 + 一套工具，自主完成「理解 → 规划 → 调用工具 → 汇总」的循环（如当前 Raven + FAC 的典型用法）。
- **多智能体**：多个具备不同角色或能力的 Agent 协作完成复杂任务，通过**任务分解、分工、交接与共识**提高复杂问题处理能力与可维护性。

### 1.2 典型应用场景

- **研究与分析**：多源检索、综合归纳、多步推理。
- **故障排查**：信息收集 → 假设验证 → 根据结果调整策略。
- **多步数据处理**：下一步依赖上一步结果，无法预先写死流程。
- **动态 API 编排**：调用顺序与条件依赖运行时结果。
- **角色化协作**：规划者拆任务、执行者做具体操作、审阅者校验、协调者做决策与路由。

## 2. 设计模式与编排方式

### 2.1 两种编排范式

| 方式 | 特点 | 适用 |
|------|------|------|
| **LLM 驱动** | Agent 自主规划、决定下一步，使用工具与 handoff；开放性强 | 开放域、探索型任务 |
| **代码驱动** | 确定性流程：结构化输出、Agent 链、并行执行、反馈环 | 可预测、高可控场景 |

### 2.2 核心设计要素

- **角色分工**：规划者（任务分解）、执行者（具体操作）、审阅者（结果校验）、协调者（任务分发与决策）。
- **共识机制**：多 Agent 输出如何合并——多数投票、置信度加权、信任值路由等。
- **任务依赖**：用图结构显式定义调用顺序，支持并行与冲突解决。
- **可观测性**：推理轨迹、工具调用链、Token 与耗时，便于调试与成本控制。
- **拓扑与 Prompt 优化**：研究表明**拓扑结构**与 **Prompt** 共同影响效果；可引入 Multi-Agent System Search（Mass）等思路做块级/工作流级优化。

### 2.3 编排抽象：Routines 与 Handoff

- **Routine**：一组指令 + 必要工具，对应一个 Agent 的「能力包」。
- **Handoff**：将任务转交给另一个 Agent（例如从「规划」交到「执行」）。  
这样可以用「谁在什么条件下交给谁」来刻画多智能体流程，而不必写死每一步。

## 3. 主流框架与平台

### 3.1 Dify（与当前栈最贴近）

- **Agent 节点**：工作流中的「大脑」，给 LLM 对工具的**自主控制权**，按需推理与调用工具，无需预先规划每一步。
- **策略**：**Function Calling**（适合 GPT-4、Claude 3.5 等）或 **ReAct**（Thought → Action → Observation，适合无原生 function calling 的模型）。
- **多智能体**：可将多个 Agent 节点放入同一工作流，通过变量传递、条件分支、并行分支组合成多智能体流水线；串行/并行执行与变量聚合均支持。
- **与 COS 的关系**：Dify 作为可选编排层，模型可配置为 LiteLLM 端点；工具可对接 FAC MCP（HTTP 调用 tools/call），从而复用 COS/Frappe 能力。

### 3.2 LangGraph

- **特点**：基于图的状态机，擅长**带循环与条件**的复杂流程，与 LangChain 生态集成深。
- **多智能体**：通过状态图定义多 Agent 节点与边，支持多智能体协作与状态持久化。
- **落地**：可单独部署为服务，或通过 Dify 的 HTTP/Code 节点与外部 LangGraph 服务交互。

### 3.3 CrewAI

- **特点**：强调「角色化 Agent 团队」、任务链与角色分工，内置任务传递与流程控制。
- **适用**：需要明确角色（研究员、写手、审阅等）的流水线。

### 3.4 AutoGen（微软）

- **特点**：多智能体会话编排，支持自定义回复逻辑、工具调用与「辩论模式」达成共识。
- **适用**：需要精细控制对话轮次与共识形成的场景。

### 3.5 OpenAI Swarm / Agents SDK

- **特点**：Routines + Handoff 的官方抽象，多 Agent 通过 handoff 交接任务。
- **适用**：以 OpenAI 模型为主、希望用官方范式做多 Agent 时可选。

## 4. 在 COS 当前架构下的落地考量

### 4.1 现状简述

- **Raven**：用户入口，单会话中通常对应**一个 LLM + 一套 FAC 工具**（单智能体）。
- **FAC**：MCP 端点，暴露 `tools/list`、`tools/call`，带权限与审计。
- **Dify + LiteLLM**：可选；Dify 做工作流/RAG/Agent 编排，LiteLLM 统一模型接口。

### 4.2 引入多智能体的可选路径

| 路径 | 做法 | 优点 | 注意 |
|------|------|------|------|
| **A. Dify 工作流多 Agent** | 在 Dify 中建多个 Agent 节点，分别配置不同指令/工具子集，用变量与分支串联 | 与现有 Dify+LiteLLM 一致；可视化、易迭代 | 需把 FAC 工具暴露给 Dify（HTTP 封装 MCP 或 Dify 的 HTTP 工具调 FAC） |
| **B. Raven 侧多 Agent** | 在 Raven 或上游增加「协调 Agent」：先规划再路由到不同专业 Agent（各自调 FAC 子集） | 用户仍从 Raven 入口进入 | 依赖 Raven 是否支持多 Agent/多会话编排，需查 Raven 能力 |
| **C. 独立编排层** | 用 LangGraph/CrewAI 等单独部署编排服务，对外提供 API；Raven/Dify 调该 API | 架构清晰、框架自由 | 多一层运维与权限边界 |

### 4.3 与 FAC / 权限 / 审计的衔接

- **工具边界**：每个 Agent 应只持有完成任务所需的 FAC 工具子集（按角色做工具白名单），避免权限放大。
- **审计**：所有对 FAC 的 `tools/call` 仍经 FAC 审计；多智能体编排层需在日志中带上「调用方 Agent / 工作流 run_id」，便于溯源。
- **成本与限流**：多 Agent 会放大 Token 与调用次数；在 LiteLLM 或 Dify 侧做计量、配额与熔断，与现有「LLM Gateway」目标一致。

### 4.4 落地优先级建议

1. **短期**：继续夯实单智能体（Raven + FAC + COS 工具），把「物料/单据草稿」等首批能力做稳。
2. **中期**：若需「规划 → 执行 → 审阅」等分工，优先在 **Dify 工作流**中做多 Agent 试点（2～3 个 Agent 节点 + 变量传递），FAC 工具通过 Dify HTTP 工具或 MCP 桥接暴露。
3. **长期**：若 Dify 无法满足复杂图或状态需求，再评估引入 LangGraph 等独立编排层，并与 FAC 权限/审计体系对齐。
